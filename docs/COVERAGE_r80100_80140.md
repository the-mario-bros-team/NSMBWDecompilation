# Coverage - `r80100_80140` (main.dol `0x80100000..0x80140000`)

## How to read this file

This is the coverage record for lane 10, the unclassified main-`DOL` text range
from `0x80100000` (inclusive) to `0x80140000` (exclusive). The thirteen
engine-global helpers (clusters A-C) were promoted to
[`src/engine/globals.rs`](../src/engine/globals.rs); the fifteen WorldMap and
r2/float helpers (clusters D-E) were promoted to
[`src/game/worldmap.rs`](../src/game/worldmap.rs) in a second pass. The staging
file [`src/subsystems/r80100_80140.rs`](../src/subsystems/r80100_80140.rs) now
holds only its module header.

- **Address** is the entry virtual address from
  `work/ghidra/main-gb/export/functions.tsv`; it is not a file offset.
- **Status** follows `docs/RUST_STYLE.md`: `translated` = full control flow and
  all evidence calls are represented; `partial` = major effects only; `stub` =
  address/role only.
- **Confidence** measures evidence strength, not code quality:
  `high` = body is explicit and unambiguous; `medium` = role or a callee
  argument is inferred; `low` = mostly unknown.
- **Evidence** is the per-function Ghidra C file under
  `work/ghidra/main-gb/export/`.
- Every Rust function has an `# Original` block with the same address and file.
- **Appendix A** is the machine-readable inventory of all eligible entries in
  the range. Use it to pick the next translation target; no address appears
  there twice.

Terms: `DOL` is the Wii executable container; `r13` is the PowerPC small-data
base register; `SDA` means small-data area. See `docs/GLOSSARY.md`.

## Clusters

### A. Four-slot global state (`0x80101950..0x80102220`, 10 functions, 580 bytes) - promoted to `engine/globals.rs`

A compact group of accessors and teardown helpers around a four-element array
at `0x803741D0`. The slot count is hard-coded as four in both loops
(`0x801020F0`, `0x80102140`), so it is `observed`, not a guess.

Call relationships:

```
0x80102220  any-slot? (0x801021B0)
            -> 0x801020F0  for i in 0..4
               -> 0x80102060
                  -> 0x8008F310(slot+0x40)        busy test
                  -> *(vtable+8)(slot, 1)          virtual destructor
0x80102140  -> 0x800DDC50(slot?) per non-null slot
0x801021D0  -> 0x8016E7F0(a,b,c,d,0x20,4)          lazy pool
0x80101BC0  -> table 0x802F4A18[index] -> SDA
```

`0x80102060` is the only function in this cluster with a proven virtual call:
it loads the object's first word, reads `+8`, and calls it with `(object, 1)`.
That is the classic deleting-destructor shape (`// inferred:`). The call to
`0x8008F310` before it is a "still busy" gate: a zero return leaves the slot
untouched.

The other accessors (`0x80101950`, `0x80101960`, `0x80101FD0`, `0x801021B0`,
`0x801021D0`) are role-inferred from their shape. No string or RTTI name ties
them to a gameplay subsystem.

### B. Bit-mask table and SDA reset (`0x80102750..0x80102790`, 2 functions, 108 bytes) - promoted to `engine/globals.rs`

`0x80102750` indexes a table of 42-word rows (`0xA8` bytes per row) and returns
whether any bit overlaps. The literal expression in Ghidra is
`(-x | x) >> 31`, a sign-bit extraction equivalent to `x != 0`. The column
bound `0x2A` is explicit; the row bound is not, so the caller owns it.

`0x80102790` is a seven-store reset. The copy-then-clear order matters:
`0x8042A25B` receives `0x8042A25A`, and `0x8042A25D` receives `0x8042A25C`,
before both sources are zeroed. The Rust body keeps that order exactly.

### C. Packed identifier (`0x80102A60`, 1 function, 20 bytes) - promoted to `engine/globals.rs`

`fn_80102a60` is a pure expression:
`(low & 0xFF) | (high << 8) | (mid << 4)`. Bits 4-7 are shared by `low` and
`mid`, so the OR order is observable. The field meanings are unknown; the
function is included because it is completely determined and is called by the
effect-spawn path at `0x80102690`.

### D. WorldMap effect slot table (`0x80102F90..0x80103ED0`, 7 functions, 564 bytes) - promoted to `game/worldmap.rs`

The strongest cluster in this pass, because the neighbouring function
`0x80103580` (not translated here) returns 47 case labels with strings such as:

- `Wm_cs_mrlandsmoke`
- `Wm_cs_footsmoke`
- `Wm_cs_landwater`
- `Wm_en_burst_m`
- `Wm_cs_killershot`

`Wm_` is the WorldMap subsystem prefix (`// inferred:` from the names; the game
has a WorldMap directory in its FST). The slot geometry is:

| Property | Value | Evidence |
|---|---:|---|
| Record stride | `0x150` | `0x801034E0`, `0x80103150`, `0x80103440` |
| Record count | `0x55` (85) | `0x80103150` loop, `0x80103500` scan |
| Active byte | `base + (index+1) * 0x150` | `0x801034E0`, `0x80103500`, `0x80103440` |
| Sub-object | `slot + 0x24` | `0x80102F90`, `0x80103000` |
| Sub-object vtable | `0x80329958` | `0x80102F90`, `0x80103000` |

The active byte sits at the **start of the next record**, not at `slot+0`.
This is unusual but appears consistently in four independent functions, so the
Rust keeps the literal offset instead of normalising the layout. `0x80103150`
therefore clears one byte past the last record; the region it requires is
`0x55 * 0x150 + 1 = 0x6F91` bytes.

Call relationships:

```
0x80103150  init 0x55 records, clear trailing active byte
0x80103500  scan active bytes -> free index or -1
0x80103440  allocator (not translated): find -> write fields -> set +0x150 = 1
0x801034E0  clear active byte for one index
0x80103220  update one slot (not translated): name -> 0x802E1BD0 -> virtual +0xA0
0x80102F90  construct sub-object at +0x24
0x80103000  destroy sub-object at +0x24, optionally free slot
0x80103ED0  teardown wrapper
```

## Uncertainties

1. **`r13` base is verified, but the repository glossary still calls it
   unknown.** `0x800041C0` contains `addis r13,0,0x8042` / `ori r13,r13,0xF680`
   / `blr` (bytes `3D A0 80 42 61 AD F6 80 4E 80 00 20` at ELF offset 0x444),
   so every SDA absolute address in `src/engine/globals.rs` and
   `src/game/worldmap.rs` is `0x8042F680 + offset`.
2. **`r2` base is verified as `0x80433080`; three r2-dependent bodies remain
   deferred.** `0x80102DB0` and `0x80103B40`, plus the GQR-heavy `0x80101AA0`,
   still contain paired-single decompiler artifacts (and `0x80103B40` divides
   by `uVar4 * (1 - uVar4)`), so they were not translated from the C alone.
   The ordinary r2 constants used by the other eight functions are listed in
   cluster E and are resolved exactly.
3. **Dropped callee arguments.** Ghidra prints `FUN_800DDC50()` in
   `0x80102140` and `FUN_802B9280()` in `0x80103ED0`. The sibling destructor
   `0x80103000` proves that `0x802B9280` can take the object pointer, but this
   lane did not recover the actual register setup. Both Rust functions use the
   literal `call0` and are marked `medium`.
4. **Slot active-byte layout.** The `+0x150` flag offset is consistent across
   four functions but does not match a conventional `slot+0` flag. It may mean
   the caller passes a pointer `0x150` before the array, or the records may
   interleave data and flags. The Rust preserves the offset; the allocator
   `0x80103440` is the next function that will settle the semantics.
5. **Roles are mostly inferred from shape.** Only `0x80103580` has strings that
   name the subsystem. `fn_80101950`, `fn_80101960`, `fn_80101fd0`,
   `fn_801021d0` and `fn_80103ed0` have no direct naming evidence.
6. **`fn_801021d0` divides by `param_3` without a check.** The original PowerPC
   `divwu` has undefined behaviour for zero; the Rust expression will panic on
   a host build. It is a source reconstruction, not a runnable port.
7. **`fn_80102060` calls the virtual destructor with argument 1.** The
   "deleting destructor" interpretation is inferred from the `(this, 1)`
   convention; the method's actual name and ownership semantics are unknown.
8. **`fn_80103d90` read order is preserved** (`src[1]`, `src[2]`, `src[0]`).
   This only matters for overlapping source/destination, which the original
   may or may not allow.
9. **Float-call ABI is declared, not runtime-verified.** `0x80103840` calls
   `0x80237BD0` as `f64 -> f64`; the `0x80106xxx` constructors call
   `0x8022D2F0` as `(f64, f64, u32)`. Those prototypes come from Ghidra and
   match the 32-bit PowerPC EABI, but no runtime test exists.
10. **`fn_80106c70` returns `-1.0` when the match is on the last visited
    vector.** The branch is explicit (`visited == count + 1`), but its gameplay
    meaning is unknown; the function is therefore `medium`.
