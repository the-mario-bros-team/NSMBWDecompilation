### Selection rule actually used

The task asked for up to 20 functions of 64–4096 bytes with clear evidence.
Twenty were chosen; `vec2_sub` (`0x8000D870`, 36 B) and `fn_8000e030`
(`0x8000E030`, 48 B) were added as **helpers**: `vec2_sub` is called by
`vec2_differs_from`, and `fn_8000e030` documents the rail record layout (it is
called from `0x8000F950`, a next target). They are counted separately in the
summary table above (22 total).

There are no string cross-references in this range (`s_*` names appear only at
`0x800129A0`), so selection had to rely on **recognisable call shapes and
structure**:

* "12 consecutive `lfs`/`stfs`" → `copy_12_floats`;
* four identical `stfs` groups with stride `0x3390` → four-lane storage;
* the `if (obj) { dynamic-cast; iterate }` prologue repeated five times → the
  path-node cluster;
* two loops whose array offsets tile each other exactly (`0x2738+2000=0x2F08`,
  …, `0x4678+6000=0x5DE8`) → 500-entry record layout;
* `GXBegin(0x80, 0, 4)` followed by `stfs`/`stb` to `0xCC008000` → quad
  emission.

## Clusters

### A. Four-lane vertex grid — `0x8000D0A0..0x8000D0D0` → `src/render/geometry.rs`

`store_four_lane_vertices` (`#3`) writes index `i` of four parallel arrays:
lane `k` at `object + 0x48 + k*0x3390`, component `x/y/z` at `+0/+4/+8`, entry
size 12 bytes.

Cross-check inside the image: only one other function mentions `0x3390`
(`0x80100530`, which *reads* `*(int *)(this + 0x3390)`), so the stride is not a
coincidence of one function. The sibling `0x8000D0A0` (44 bytes, not selected)
writes a *single* lane: `object + layer*0x3390 + 0x48 + index*0xC` — same
layout, which is what pins the interpretation.

`copy_12_floats` (`#1`) copies exactly the 12 floats that this store consumes
(three `Vec4`s, or four `Vec3`s — the caller's framing is unknown).

`fn_8000b320` (`#2`) publishes one 2-float point into the same sub-object family
(`object + 8 + index*0x20`) through `0x802C7C70`. It is grouped with vertex
storage because it has no collection/iterator work, unlike the path cluster.

### B. Node-array initialisers — `0x80008440`, `0x800099D0` → `src/game/actor.rs`

These two are the largest clean functions in the range and reveal object
layouts by construction:

**150-entry object (`0x80008440`)**

| offset | contents | end |
|---|---|---|
| `+0x038` | `u8[150]` | `+0x0CE` |
| `+0x0D0` | `f32[150]` | `+0x328` |
| `+0x328` | `f32[150]` | `+0x580` |
| `+0x580` | `Vec3[150]` (12 B) | `+0xC88` |

The compiler unrolled the loop 8× and peeled 6 entries (144 + 6 = 150). The
Rust keeps the 150 updates as one loop and says so in the doc comment.

**500-entry object (`0x800099D0`)**

| offset | contents | end |
|---|---|---|
| `+0x0FC8` | `f32[500]` | `+0x17B8` |
| `+0x1F68` | `f32[500]` | `+0x2738` |
| `+0x2738` | `u32[500]` colour `0xFFFFFF00` | `+0x2F08` |

### C. Path-node accessors — `0x8000D190`, `0x8000D260`, `0x8000D3B0`, `0x8000D5B0`, `0x8000D660` → `src/game/path.rs`

All five share one skeleton:

```
manager = [this+4]
if manager != 0:
    if virtual_slot_2(manager, &type_descriptor_0x802F8FF0) != 0:
        ... collection / iterator / node work ...
```

`0x8023B8C0`/`0x8023B860`/`0x8023B800` export the collection (count / element /
lookup), `0x8025C4C0`/`0x8025C560` read iterator elements, and
`0x8023D0A0`/`0x8023D300`/`0x8023D3C0`/`0x8023D460`/`0x8023D520` read and write
node payloads. All of them live in other lanes, so the Rust calls them by
address and documents the argument shape observed at each site.

The `+0x3C` relative-offset idiom (`node = element + [element+0x3C]`, else null)
is visible in three of the five functions.

### D. Rail follower — `0x8000DE70`, `0x8000DF60`, `0x8000E030`, `0x8000E840` → `src/game/path.rs`

Follower object layout (recovered):

* `+0x30` / `+0x34` — anchor point `x` / `y`
* `+0x38` — anchor `u16` third field; also the entry count for `fn_8000e030`
* `+0x3C .. +0xC30` — 255 record slots of `{f32 x, f32 y, u16 z, u16 pad}`
* `+0xC30` — follower speed (`f32`)
* `+0xC34` — encoded count: `2*points + 2`, zero when nothing was appended

`0x8000DF60` is the only function in the range whose loop was reconstructed
from the **assembly** rather than the C: Ghidra emitted
`uVar8 = FUN_802dcd6c(); iVar2 = high; puVar7 = low;` which is not a real call
(see "Ghidra artefact" below). The rebuilt loop reads the anchor, appends every
point that differs from the last accepted one, and stops at the buffer end
(`cmpw r29,r28; beq`).

### E. GX quad emission — `0x8000EBF0`, `0x8000EEB0`, `0x8000EF20` → `src/render/gx.rs`

`0x8000EBF0` writes four corners to `0xCC008000` (GX write-gather FIFO):
three `f32` position components per corner plus two optional bytes,
preceded by `0x801C5570(0x80, 0, 4)` (`GX_QUADS`, vertex format 0, 4
vertices — inferred from the arguments and the following FIFO stream).

`0x8000EEB0` / `0x8000EF20` are wrappers that copy two 2D points onto the stack
and call `0x8000E910` (quad fill), `0x8000EBF0` (corner emission) and
`0x8000EDD0` (flush). `0x8000EF20` additionally emits
`0x801C47D0(0,0,0,0x1E,0,0x7D)` and `0x801C9A80(param,0x1E,0)`; `0x1E`=30 and
`0x7D`=125 are passed literally.

`// unknown:` the two trailing bytes per corner are not identified (texture
coordinates in a packed format or a per-corner index both fit).

### F. Object construction — `0x8000F460`, `0x8000F4B0` → `src/game/actor.rs`

`0x8000F460` is a constructor: it forwards three arguments to `0x80258710`
(which stores two of them at `+0xDC`/`+0xE0` and ORs `0x60000000` into
`+0xCC`), then installs vtable `0x802FE448` and rewrites the flag word
(`clear 0x40000000`, `set 0x20000000`).

`0x8000F4B0` is a sized factory: allocator slot `+0x14` of the object at
`[owner+0x14]` is called as `alloc(allocator, index*4 + 0xE8, 4)`, then the
constructor is applied with `(owner, new+0xE8, index)`, then `0x80257640`
applies the label. The allocation-size rounding in the assembly
(`(index*4 + 0xEB) & ~3`) is a no-op and documented as such.

### G. Vector math — `0x8000D870`, `0x8000D8A0`, `0x8000F900` → `src/render/geometry.rs`

Small, self-contained, and the only functions in the range with no cross-lane
calls except `0x802BE470` (length).

## Ghidra artefact worth knowing for every lane

Ghidra lists `0x802DCD18 .. 0x802DCDBC` as a run of 4-byte "functions"
(`FUN_802DCD40`, `FUN_802DCD64`, `FUN_802DCD6C`, `FUN_802DCD70`, …) whose bodies
are only `stw rN, -k(r11)`. These are **Metrowerks prologue/epilogue save
helpers** (`_savegprlr_N` / `_restgprlr_N`), not callable game functions.

As a result the decompiler prints things like

```c
uVar8 = FUN_802dcd6c();          /* 0x8000DF60 */
iVar2 = (int)((ulonglong)uVar8 >> 0x20);
puVar7 = (undefined4 *)uVar8;
```

which would be nonsense if translated literally: the real instruction is
`addi r11,r1,0x30 ; bl 0x802dcd6c`, i.e. *spill r26..r31 into the frame*. The
same pattern appears in `0x8000F950`, `0x800099D0`, `0x8000B370` and many
others. **Do not translate these as calls.** In this lane the affected
functions were checked against the raw instruction words and the prologue is
omitted from the Rust (the Rust compiler emits its own prologue).

Likewise, `0x80007510` is a 4-byte tail thunk (`b 0x80164FD0`); calls to it are
translated as calls to `0x80164FD0`.

## Uncertainties and limitations

1. **`0x802BE470` is named `sqrt` only by shape.** Its body calls
   `0x802E8620` and narrows the result through `f32`; the caller feeds it
   `dx*dx + dy*dy`. The Rust documents it as `// inferred:` and returns `f64`.
2. **Node API semantics.** The five path-node accessors reproduce argument
   order and iteration exactly, but what a "node", a "collection" and the
   `+0x3C` relative offset mean is owned by the `0x8023xxxx` lane. Confidence
   is therefore `medium`, not `high`.
3. **Colour word `0xFFFFFF00`.** The value is exact (read from `0x8042B0D0`);
   the channel order (A/R/G/B vs. R/G/B/A) and whether the zero byte is alpha
   are unknown.
4. **Two trailing bytes per quad corner** (`0x8000EBF0`): emitted only when
   `param_2 != 0`; not identified.
5. **Float pass-through in `0x8000EEB0`/`0x8000EF20`.** The original wrappers
   never write `f1`, so `0x8000E910`'s first (double) argument is whatever the
   caller of the wrapper left there. Ghidra shows no float parameter for the
   wrappers. Wave 234 therefore gave both Rust signatures an explicit
   `translate: f32` first parameter (the ABI register they always inherited)
   and forward it to `0x8000E910` in `f1`; every call site was updated. This is a
   property of the original ABI usage, not a missing translation.
6. **`vec2_differs_from` boundary values.** The C pseudocode uses
   `dx < eps && -eps < dx && ...`; the compiled form is `fcmpo` + `cror`
   (>= / <=-style predicate). They differ only when a component equals the
   tolerance exactly or is NaN. The Rust follows the pseudocode and says so.
7. **Collapsed unrolled loops.** `0x80008440` (8× unroll + 6-entry peel) and
   `0x800099D0` (2× unroll) are written as canonical loops. The set of stores
   is identical; the instruction-level shape is not reproduced. This is called
   out in both doc comments.
8. **`0x8000F460`'s class identity.** The vtable `0x802FE448` is exact; there
   is no RTTI string for it in the image, so the class name is unknown.
9. **`0x8000F4B0` allocator interface.** Slot `+0x14` of the allocator vtable
   is called with `(allocator, size, 4)`; the exact allocator type is not
   resolved (RAII/heap lane).
10. **No runtime validation.** `cargo check` proves the module type-checks; it
    does not execute the PowerPC code. Constants were cross-checked against
    `work/dol/main.elf` data, and call targets against the instruction words.

## Method and verification

1. **Inventory.** Read `work/ghidra/main-gb/export/functions.tsv`, filtered
   entries with `0x80005000 <= entry < 0x80014000`, and dropped the eight
   entries shorter than 16 bytes.
2. **Evidence.** Read the Ghidra C for candidate functions
   (`<addr>_<name>.c`, lowercase hex).
3. **Instruction check.** For every selected function, the raw big-endian
   instruction words were read out of `work/dol/main.elf` (ELF32 BE program
   headers → virtual address to file offset), primarily to verify `bl` targets
   and to detect Ghidra prologue artefacts. This caught:
   * `0x80007510` being a thunk to `0x80164FD0`,
   * `0x802DCD6C` being a save-register helper, not a call,
   * the exact argument registers of `0x8000DE70`/`0x8000E840`/`0x80008440`/
     `0x800099D0`,
   * the two `0x8000EBF0` corner tables and their `flip` selection.
4. **Constants.** Floats/words read through `r2` were resolved by evaluating
   `r2 = 0x80433080` (set at `0x8000423C`) and reading the image at the
   resulting address (`0x8042B0A0` = `0.0f`, `0x8042B0F0` = `0.1f`,
   `0x8042B0D0` = `0xFFFFFF00`, `0x8042B118` = `1.0f`, `0x8042B11C` = `0.0f`).
5. **Compile check.** `cargo check` succeeds with 0 errors and 0 warnings in
   the four destination modules. `node tools/doc-lint.mjs src` reports 0
   violations. Promotion only moved definitions, so the checked behaviour is
   unchanged.
