## Evidence quality notes

* **Ghidra caveats.** The export contains
  `WARNING: Could not recover jumptable` (e.g. `0x8014ED14`, `0x802DCBFC`),
  `Removing unreachable block`, and `unaff_r2`/`unaff_r13` placeholders. A
  function with a jump-table warning is still translatable, but its switch
  arms are not trustworthy; none of the twenty translated functions has one
  except the indirect call in `0x8014ED00`, which is marked `partial`.
* **`r13` is known.** `0x800041C0` sets `r13 = 0x8042F680`; this is already
  recorded as `SDA_BASE` in `src/engine/startup.rs`. So `unaff_r13` functions
  in this lane (for example `0x80145E90`, `0x8015BE60`, `0x8015D3A0`) are
  tractable: replace `unaff_r13 - k` with `0x8042F680 - k`.
* **`r2` is not known.** `unaff_r2` appears in float-heavy world-map effects
  (`0x8014CDD0`, `0x8014F470`, `0x8014F630`, `0x8016C9E0`'s callees). `r2` is
  the SDA2 base and differs from `r13`; it is not recovered by this export.
  Those functions are listed as later targets, not silently approximated.
* **Lost call arguments.** Ghidra occasionally drops the operands of an
  indirect or thunk call (`0x8014ED00`'s slot `+0x18`, `0x802E1AB4` in
  `0x8016D180`, `0x80162D00` inside `0x8014E9B0`). The affected rows are
  marked `partial`/`medium`; the Rust doc comments explain what was inferred.
* **Float ABI.** `FUN_8008C570` is declared `double` but every call site
  promotes the result with `(double)`. Its body is a two-float add, so
  `wm_consider_candidate` inlines that add rather than guessing the ABI.
  The `0x801C0BD0`/`0x801C0C60` layout calls genuinely take `double` (their
  definitions say so), and the Rust code passes `f64`.
* **Duplicate initialisers.** `0x80153400` (daYoshi), `0x80159F10`
  (dGameDisplay) and `0x8015DDD0` (dScBoot) are not control-flow mazes: they
  are long sequences of "construct state descriptor, copy 10 words, register".
  They are large but mechanical; expect high confidence once one family is
  decoded.
* **Promotion scope.** The moves changed file ownership, not behaviour. The
  only code edits were private one-line ABI adapters needed because each
  destination module is self-contained (for `ui/lyt.rs`, `read_f32(addr)` and
  the existing `call4` replaced the staging file's two-argument `read_f32` and
  `call4_u32`); every translated store, call and branch is the same as in the
  staging file. The final pass followed the same rule: `worldmap.rs` already
  had `flag_test`, so `flag_set`/`flag_clear` (mirrors of `0x80056C70` /
  `0x80056CB0`) were added beside it, and `task.rs` got local `read_half`,
  `write_half` and `vcall0` helpers. No condition, call order or store changed.
* **Promotion gates (2026-11-01, `ui/lyt.rs` pass).** `cargo check` and
  `node tools/doc-lint.mjs src` both pass (0 errors, 0 violations). The crate
  check was rerun after concurrent edits in other lanes settled; no diagnostic
  referenced this lane's files. While those lanes were still editing, the moved
  code was additionally compiled in an isolated scratch crate with 0 errors.
* **Promotion gates (2026-11-01, final pass).** `cargo check` and
  `node tools/doc-lint.mjs src` both pass (0 errors, 0 violations) after the
  four remaining functions moved. `src/subsystems/r80140_80180.rs` has no code

## Uncertainties

1. `0x8014ED00` - the indirect call at vtable slot `+0x18` has no operands in
   the C output. The Rust signature forwards an `event` pointer because both
   call sites pass `&DAT_80376f08` / `&DAT_80376f48`. Now in
   `src/game/interaction.rs`.
2. `0x8016D180` - `0x802E1AB4` is called with one argument. Its other role in
   `0x8014A5D0` is a `strcmp`-shaped comparison, so the Rust code treats the
   one-argument form as a name check and marks the branch `unknown`. Now in
   `src/ui/lyt.rs`.
3. Field meanings are inferred, not proven:
   `+0x36C` attachment state, `+0x36D` candidate sub-kind, `+0x38C` "ready",
   `+0x43C` hold timer, `+0x1070` animation id, `+0x153C` mode byte,
   `+0x1541` colour/variant byte, `+0x1558/+0x155C/+0x1560` candidate cache,
   `+0x1564/+0x1568` retry counters.
4. `0x8016EF50` - the call order is Y (second component), X (first), Z
   (third): `0x8016EDD0`, `0x8016ECB0`, `0x8016EEF0`. The axis *names* come
   from the callee sequence, not from a recovered header. Its caller
   `layout_set_transform` is now in `src/ui/lyt.rs`; `0x8016EF50` itself is
   still untranslated.
5. `wm_update_held_item` - type id `0x97` and flag bits `0x10/0x20` at
   `+0x120` are observed, but "held item" is inferred from the shape. It now
   lives in `src/game/worldmap.rs` with an explicit `medium` confidence; a
   caller that proves the role should upgrade the note, not move the code.
6. Functions called by address outside this lane (`0x801299B0`,
   `0x80060720/50`, `0x801C....`) are not translated; their effects are
   documented only as far as the call site shows.
7. The three task/state helpers (`step_angle_toward`, `run_task_list`,
   `keys_equal`) have clear bodies and are now in `src/game/task.rs`. Their
   *callers* are still untranslated, so the task header's `0x8015F600`
   initialiser and the state-object constructor `0x8015F7C0` remain the open
   evidence for the cluster.
