# Coverage — `0x80200000..0x8025FFFF` (`r80200_80260`)

## How to read this file

This is the status page for one address lane of the `main.dol` reconstruction.
It answers three questions:

1. **What is in this range?** — the *Range inventory* section: how many function
   entries exist, how many are eligible, and how they are distributed.
2. **What did this pass translate and promote?** — the *Promoted functions*
   table: one row per function, with the address, the Rust name, the role (plain
   English), the status, the confidence and the Ghidra evidence file.
3. **What should the next pass do?** — the *Clusters* and *Next targets*
   sections, plus *Uncertainties* so the next agent does not redo or over-trust
   this work.

Column meanings:

- **Status** — `promoted` = translated and physically moved to its semantic
  module (`src/runtime/bt.rs`); `translated` = full control flow and every call
  accounted for, still staged; `partial` = entry/exit and major effects, body
  incomplete; `stub` = address only. Every row below is `promoted`.
- **Confidence** — strength of the *evidence*, not code quality:
  `high` = the bytes/flow are explicit and cross-checked by a caller;
  `medium` = flow is explicit but a role or a data table is not proven;
  `low` = mostly guesswork.
- **Evidence** — path under `work/ghidra/main-gb/export/`; that C file is the
  source of truth.

The Rust now lives in `src/runtime/bt.rs`, organised by Bluetooth layer; the
staging file `src/subsystems/r80200_80260.rs` is a pointer only. The
machine-readable ledger is `ledger/agents/r80200_80260.csv`. Addresses are
virtual addresses of the unrelocated `main.dol` (image base `0x80004000`), not
file offsets.

Legend for inline markers used in the Rust (see `docs/RUST_STYLE.md`):
`// observed:` = visible in Ghidra output, `// inferred:` = role guessed from
callers/strings, `// unknown:` = unresolved.

## Clusters

The range is not homogeneous. The 20 translations were chosen to sample each
cluster with at least one *complete* function so the next pass has a foothold.

### A. HID-host 4-slot bookkeeping — `0x80200000..0x8020117C` (19 entries)

Four per-device control blocks at `0x803D1BAC`, stride `0x11C`:

| Offset | Type | Meaning |
|---|---|---|
| `+0x00` | `u16` | slot id / connection handle |
| `+0x08` | 6 bytes | `BD_ADDR` (observed in `80200310_FUN_80200310.c`) |
| `+0x119` | `u8` | in-use flag |
| `+0x11A` | `u8` | per-slot byte set from the connect callback |

Promoted (`src/runtime/bt.rs`): `fn_80200000`, `fn_8020028c`, `fn_802006e8`,
`fn_8020117c`.
The big members still open are the connect/disconnect handlers
`0x80200310` (788 B) and `0x80200624` (196 B).

### B. BTM device database and connection callback — `0x80201710..0x802024E8` (15 entries)

16 records at `0x803D3AA8`, stride `0x88`, `BD_ADDR` at `+0x1C`, flags at
`+0x76` (bit `0x80` = occupied). The single connection callback lives at
`0x803D2040` and is invoked with five arguments.

Promoted (`src/runtime/bt.rs`): `fn_80201710`, `fn_8020213c`, `fn_80202460`.

### C. HCI command builders — `0x8020E74C..0x8020F1C4` (19 entries; 30 in the wider `0x8020E000..0x8020F2FF` family)

A family of small functions that fill an HCI command buffer and queue it via
`0x8020AC78`. Common layout (observed across all three promoted members):

| Offset | Type | Meaning |
|---|---|---|
| `+0x02` | `u16` | packet tag (3, 4 or 5 — meaning unknown) |
| `+0x04` | `u16` | cleared (unknown) |
| `+0x08` | `u16` LE | HCI opcode |
| `+0x0A` | `u8` | parameter length |
| `+0x0B` | … | parameters |

Promoted (`src/runtime/bt.rs`): `fn_8020e74c`, `fn_8020ec28`, `fn_8020f1c4`.
The queue routine `0x8020AC78` itself is *not* translated (it is a 396-byte
BTM function).

### D. L2CAP registration — `0x80212648..0x80213240` (15 entries)

`fn_80212648` deregisters PSMs `0x11`/`0x13`; `fn_80213220` is the trace-level
accessor. The worker `0x80212810` (144 B, sender of the `L2CA_Deregister`
string) and the `0x80213120`/`0x80213240` pair are next.

### E. RFCOMM/PORT — `0x80218DDC..0x8021E44C` (71 entries)

Channel block → port block resolution (`fn_80219e40`) and a checksum helper
(`fn_8021e44c`). The layer is identified by the `PORT_DlcEstablishCnf` string
in `80218ddc_FUN_80218ddc.c`.

### F. Utility helpers — `0x80228DD0..0x8025FFFF` (643 entries)

Unrelated small helpers sampled across the last four blocks:
record zero-init (`fn_80228dd0`), tagged 6-byte serialiser (`fn_80239a10`),
fixed-stride table index (`fn_8024d390`). These were chosen for clarity, not
because the surrounding functions are understood. They were promoted to
`src/runtime/bt.rs` under **utilities** so they are not lost, but their
Bluetooth role is *not* proven; see Uncertainty 8.

## Uncertainties

1. **Dropped call arguments.** Ghidra prints `FUN_8020AC78();` inside the three
   HCI builders, i.e. it did not propagate `r3`. The Rust passes the command
   buffer explicitly, marked `// inferred:`. Supporting evidence: `0x8020AC78`
   reads the header fields (`+4`, `+8`, `+9`) exactly as the builders write
   them, and the builders do not clobber `r3` before the call, so the buffer is
   the only value that can arrive in the first argument. This is the one place
   where the translation adds an argument the C does not show.
2. **Checksum table.** `0x8021E44C` folds bytes through `0x802F7098`
   (256 bytes in `.data`). The table contents are not part of the C export, so
   the algorithm is reproduced structurally, not by polynomial. The
   "checksum" label is inferred from the append-at-`+0x14` caller.
3. **`0x803DFFB4` table.** `fn_8024d390` is exact, but the record role is
   unknown. The only caller branches on the `0x04`, `0x01` and `0x02` flag bits
   inside transform-heavy code, which suggests animation/collision data, but
   nothing in this lane proves it. Do not name it without new evidence.
4. **Byte meanings in `fn_80200000`.** The control-flow and memory effects are
   certain; what `+0x12`, `+0x16`, `+0x1C` and the `0x10` status value *mean*
   is not. The function is marked `medium` for that reason.
5. **Opcode names.** `0x0C18` is proven `Write_Page_Timeout` by the caller's
   log string. `0x1005` and `0x0C43` are proven opcodes but not proven names;
   they stay `// unknown:` in the Rust.
6. **Layer boundaries.** The BTM/L2CAP/RFCOMM labels come from assertion
   strings in *callers*, not from this lane's own functions. They are reliable
   for grouping, but individual functions may belong to a neighbouring layer.
7. **`r13`-relative globals.** Several neighbours of the translated functions
   use `unaff_r13` offsets instead of absolute addresses. They were skipped on
   purpose: encoding them would require guessing the SDA base. `0x8042F680` is
   the base used by the boot lane (`src/engine/startup.rs`), but that is not
   proof for this region.
8. **Utility classification.** `fn_80228dd0`, `fn_80239a10` and `fn_8024d390`
   are complete translations but their subsystem is unproven. They live in
   `src/runtime/bt.rs` under "Utilities" because the promotion map assigns
   mixed-layer helpers from this range there; `fn_8024d390`'s table looks more
   like animation/collision data than Bluetooth. If a later lane proves a
   different owner, move the function and update the ledger — do not copy it.
